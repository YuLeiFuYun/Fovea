# 数学化工程准入标准

> **状态：Active / Release-gating。** 本标准约束 Fovea 的架构、算法、资源参数、状态机、实验结论和“最优”声明。数学不是装饰性引用；不能形成可审查证明义务的理论不得改变生产设计。

## 1. 基本原则

Fovea 不接受“看起来更快”“某篇论文说更好”“某个常数在当前 benchmark 有效”作为生产准入理由。每个非平凡设计决定必须回答：

1. 被优化的对象和目标函数是什么；
2. 决策变量、约束和环境假设是什么；
3. 正确性不变量与活性条件是什么；
4. 最坏情况、资源上界和失败闭包是什么；
5. 结论属于哪一种可证明声明；
6. Swift 实现如何映射到抽象模型；
7. 哪些反例会推翻结论；
8. 哪些证据只能说明经验表现，不能说明定理成立。

没有单一实现能在所有未知硬件、网络、请求序列和多目标权重下绝对最优。Fovea 的目标不是回避这一事实，而是把每一个“最好”声明缩小到可证明且对产品有意义的域，并在所有预注册、语义可比的经验域内保持显著占优。

## 2. 声明类型系统

所有数学与性能声明必须声明以下一种类型，禁止混用：

- `universal-safety`：所有允许执行均保持不变量；
- `liveness-under-fairness`：在明确公平与最终完成假设下必然收敛；
- `exact-finite-optimum`：有限状态或有限 trace 上求得精确最优值；
- `competitive-bound`：在线算法相对离线最优的竞争比；
- `regret-bound`：累计损失相对基线或 oracle 的 regret 上界；
- `local-optimum`：在固定模型、邻域和约束下局部最优；
- `pareto-optimum`：在声明目标向量和可行域中不可被支配；
- `probabilistic-bound`：在明确随机性、独立性和置信水平下成立；
- `empirical-dominance`：仅覆盖预注册环境与样本分布的经验占优；
- `impossibility-bound`：证明不存在满足更强全称要求的算法或参数。

使用“最优”“最好”“保证”“完整”时，必须同时给出 `claimClass`、`domain`、`objective`、`constraints`、`assumptions`、`evidence` 和 `claimBoundary`。

## 3. 逐层证明义务

`docs/research/mathematical-proof-obligations.json` 是生产 target 的证明义务清单。每个 target 至少必须有一个条目，并覆盖与其职责相符的维度：

- 状态与事务层：安全、原子性、恢复和活性；
- 调度与并发层：线性化、无 ABA、饥饿边界和资源容量；
- 网络与缓存层：协议决策域、身份隔离、在线代价和失效语义；
- 解码与几何层：输入上界、工作集上界、误差界和输出约束；
- UI 层：状态机、迟到结果拒绝、取消和主线程工作上界；
- 组合根：安全策略单调性、能力边界和生命周期闭包；
- 可观测性：隐私非干扰、有限基数和诊断不改变业务语义。

每项义务必须包含实现到模型的 `refinementMap`。只有抽象模型而没有实现映射，只能标记为 `specified-gap`。

## 4. 优化准入协议

任何缓存、预取、调度、批处理、重试或架构重构进入生产前，必须依次通过：

1. **问题定义**：给出目标函数与可行域；
2. **基线与下界**：给出 exact oracle、竞争下界、信息论下界或明确说明不存在；
3. **候选推导**：说明算法为何来自模型，而非 benchmark 观察；
4. **正确性证明**：证明不改变安全、身份、缓存和取消语义；
5. **资源证明**：给出 CPU、内存、I/O、任务和元数据硬上界；
6. **鲁棒性**：构造 adversarial trace、分布漂移、取消和撤销反例；
7. **敏感性**：参数变化必须存在稳定平台区，不能只有单点最优；
8. **跨域验证**：至少覆盖合成边界、真实脱敏 trace、模拟器和真机中的适用子集；
9. **比较闭包**：所有预注册语义可比指标均不得退化；
10. **删除条件**：预先声明何种证据触发回滚或替换。

缺少任一步骤的优化只能处于 `research` 或 `proposed`，不能成为发布结论的一部分。

## 5. 数值参数准入

生产数值分为四类：

- `semantic`：协议或公开语义定义的常数；
- `resource-derived`：由调用方预算或另一个已验证硬上界推导；
- `theorem-derived`：由误差、概率或竞争界公式推导；
- `heuristic`：只能由实验选择，必须登记敏感性和回退。

隐藏的 benchmark 特化常数被禁止。特别是缓存容量、保留时间、激活次数和延迟窗口，不得以“刚好覆盖某个 fixture”作为依据。

`docs/research/optimization-parameter-registry.json` 记录所有自适应/优化参数。`heuristic` 参数必须同时满足：

- 单位和量纲明确；
- 候选范围在运行前预注册；
- 不引用 comparator、workload ID、fixture 名称或数据集索引；
- 有跨工作负载敏感性证据；
- 有安全默认值与禁用路径；
- 参数变化不改变身份、安全或持久化语义。

## 6. 缓存与预取的专门标准

短驻留已验证编码数据属于在线 file caching，而不是普通字典。若进入生产，必须明确：

- 容量来自显式资源预算；
- 对象尺寸、取回代价和过期语义；
- 淘汰算法的理论性质；
- 相对 exact offline oracle 的 regret；
- 对错误价值估计和分布切换的回退；
- 命名空间、generation、Vary、凭证和 no-store 隔离；
- 内存压力与撤销时的确定性清理。

固定 `512 KiB` 之类的容量只有在由外部预算或公式推导时才合法。仅因某个 W10 资源小于该值而选择它，属于 benchmark 特化，必须拒绝。

对于任意大小与取回代价的在线文件缓存，Landlord/GreedyDual-Size 提供确定性在线算法的最优竞争保证；但该定理依赖固定对象代价和容量模型。Fovea 在证明实现与该模型精确对应、处理过期和浮点/定点误差之前，不得冒用其定理。

## 7. 多目标架构最优性

架构目标至少包括：延迟、尾部、内存、I/O、能耗、代码复杂度、证明成本、API 稳定性和故障恢复。标量加权和只有在权重预先固定时才有意义。默认流程为：

1. 枚举或生成可行候选；
2. 对硬约束先做可满足性过滤；
3. 计算 Pareto 前沿；
4. 删除被严格支配的方案；
5. 对不可比较方案记录权衡，不伪造唯一总分；
6. 若选择一个前沿点，必须记录产品权重和敏感性。

“架构最好”只能表示：在声明候选空间、约束和目标向量中不存在可行方案严格支配它，并且经验指标通过预注册比较门。

## 8. 证明与实现的连接

证明链必须按以下层次闭合：

```text
需求性质
  -> 抽象状态机/优化模型
  -> 定理、模型检查或 exact oracle
  -> refinement map
  -> Swift 属性测试/差分测试/故障注入
  -> 端到端实验
```

任何一层缺失都必须在 proof obligation 中显式记录。模型检查通过不能证明 Swift 无数据竞争；基准领先不能证明状态机安全；单元测试不能证明在线最优。

## 9. 发布门

发布候选必须满足：

- 所有生产 target 已登记证明义务；
- 新增优化参数均已登记且不存在未批准的 benchmark 特化；
- 所有 `implemented` 数学理论都有存在的代码和证据路径；
- 核心状态机模型检查及 mutant 反例通过；
- 预注册可比 benchmark 在同一源码摘要上完成；
- 任一主要可比指标存在稳定落后时，禁止使用“总体最好”结论；
- 文档必须区分已证明、有限模型、经验事实和研究计划。
