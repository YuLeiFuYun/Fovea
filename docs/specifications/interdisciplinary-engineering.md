# 跨学科工程定律与发现机制

> **状态：Active 元规格。**
> 本文不扩大 Fovea 的产品范围，也不以学科类比替代代码、测试、基准或安全证明。它规定如何从数学、自然科学、生命科学、控制论、复杂性科学、人文社会科学中提炼可证伪的工程原则，并把复杂问题产生的可复用发现记录为“金蛋”。机器可验证索引位于 `../engineering-knowledge.json`。

## 1. 目的

Fovea 不以“符合当前最佳实践”为终点。项目应持续寻找比局部经验更稳定的结构：哪些不变量跨模块成立，哪些资源必须守恒，哪些反馈会失稳，哪些局部优化会产生系统外部性，哪些反复出现的问题值得沉淀为模块、工具或新规格。

跨学科推理必须同时满足三项约束：

1. **可翻译**：学科概念必须被翻译成软件中的状态、操作、边界或度量；
2. **可证伪**：必须说明什么测试、反例或数据能够推翻当前应用；
3. **有限适用**：必须记录不适用范围，禁止把隐喻升级成未经证明的“普遍真理”。

类比只负责生成候选假设。正确性仍由形式不变量、失败先行测试、差分实验、Sanitizer、变异测试、基准和生产证据裁决。

## 2. 智慧级变更标准

一次可称为“智慧级”的更新至少完成以下闭环：

```text
具体问题
→ 明确因果链与系统边界
→ 提炼可复用不变量
→ 先建立能够失败的证据
→ 最小实现或重构
→ 反例与退化路径验证
→ 文档、追踪矩阵和治理工具同步
→ 记录可复用发现或明确拒绝抽象
```

仅增加代码、增加测试数量、提高覆盖率或引用高深概念，不构成智慧级更新。变更还必须公开未证明项、测量误差和迁移成本。

## 3. 工程定律

### 3.1 FOVEA-LAW-001：不变量优先于实现

**来源：** 数学、形式方法、科学哲学。

实现会重构，类型和文件会移动，但身份隔离、事务原子性、许可容量、取消传播等不变量必须保持。设计先写“任何允许执行序列中始终为真”的命题，再选择数据结构和并发机制。

Fovea 应用：

- 同一安全域之外不得复用 record/blob；
- 被撤销 generation 的工作不得重新发布状态；
- permit 总占用不得超过容量；
- record 不得指向未发布或损坏 blob；
- 完成、失败、取消只能产生一个终态。

**证伪条件：** 存在合法调用序列违反不变量；或不变量无法在公共行为上观察，因而只是愿望。

**边界：** 不要求把所有实现形式化证明；高风险不变量优先使用模型、property test 和 mutant。

### 3.2 FOVEA-LAW-002：资源守恒与显式账本

**来源：** 物理学守恒律、会计学、经济学。

字节、像素、任务、许可、引用、文件、延迟预算和诊断容量不能凭空出现或消失。每次获取必须有唯一释放路径；每次发布必须有来源；每次删除必须考虑仍存引用。

Fovea 应用：

- `AsyncPermitPool.Permit` 使用不可复制所有权；
- cache cost、decode working set、网络 body 和磁盘 soft limit 分账；
- blob 删除前检查引用；
- diagnostics drop 显式计数；
- 回滚区分已创建 blob、已尝试 record 写入和既有 snapshot。

**证伪条件：** 计数可溢出、许可可复制、失败路径泄漏资源、指标单位混用，或账本与实际对象不一致。

**边界：** 软件资源可能被操作系统异步回收，账本描述项目可控制的逻辑所有权，不宣称覆盖全部物理资源。

### 3.3 FOVEA-LAW-003：因果顺序与局部性

**来源：** 物理学因果性、分布式系统、时序逻辑。

副作用必须发生在建立其资格的检查之后；晚到结果只能影响创建它的因果域。不得用“最终大概会取消”合理化提前创建网络任务、目录或持久状态。

Fovea 应用：

- destination/ACL/namespace 检查先于 cache/network；
- 预取消请求不创建 staging lease；
- decode 验证先于持久发布；
- generation fence 位于每个 commit checkpoint；
- UI token 阻止旧结果覆盖新 identity。

**证伪条件：** 调整调度顺序即可让无资格工作产生可观察副作用。

**边界：** 因果顺序不等于所有步骤全局串行；无共享状态的阶段仍可并行。

### 3.4 FOVEA-LAW-004：承载力与有界生态位

**来源：** 生态学承载力、种群竞争、资源生态位。

系统容量是边界，不是性能建议。等待者、缓存条目、协议字段、namespace、并发任务和诊断事件都必须有硬上限；不同工作负载不能通过共享一个模糊预算互相吞噬。

Fovea 应用：

- fetch/decode/working-set 分离许可；
- namespace registry、候选 record、header、协议数组和 ring buffer 有界；
- 大任务不能永久阻塞可容纳的小任务；
- prefetch 与交互工作未来应拥有可解释生态位。

**证伪条件：** 敌意或损坏输入可导致无界分配、无界排队或单一主体耗尽共享资源。

**边界：** 静态上限不是所有设备的最优值；平台 profile 和实测数据可调整默认值，但不得移除绝对上界。

### 3.5 FOVEA-LAW-005：反馈稳定性高于瞬时最优

**来源：** 控制论、控制工程、动态系统。

调度、缓存准入和压力响应是闭环控制问题。观测噪声、延迟和过度增益会导致振荡；因此状态变化需要 hysteresis、速率限制、稳定采样和明确的控制目标。

Fovea 应用：

- target geometry 使用增长/收缩 hysteresis；
- memory pressure 清理幂等；
- shared task 优先级随活跃订阅者升降，而非永久提升；
- retry 使用 full jitter，且尝试次数、总延迟、额外响应字节有界，`Retry-After` 不得被抖动下穿；
- 未来自适应策略必须可关闭并与固定基线比较。

**证伪条件：** 小幅输入噪声导致频繁重建、反复缓存驱逐、优先级抖动或重试风暴。

**边界：** 没有动态控制需求的路径应保持静态、简单，不为“控制论”引入多余控制器。

### 3.6 FOVEA-LAW-006：可观测性与可控制性成对设计

**来源：** 控制论、系统辨识、实验科学。

无法观察的状态不能被可靠优化；无法施加受控输入的系统也不能识别因果。每项优化应同时提供观测量、控制变量和确定性基线。

Fovea 应用：

- fetch/decode queued 与 started 分离；
- clock、transport、decoder 和 store 可注入；
- network metrics、working-set reservation、取消和回滚有结构化事件；
- benchmark 固定 workload、cache state 和网络条件。

**证伪条件：** 指标无法区分排队和执行、相关性被当因果，或优化无法在关闭状态下比较。

**边界：** 可观测性不得泄漏 URL、凭证、稳定内容摘要或账户身份。

### 3.7 FOVEA-LAW-007：熵增必须显式，原始信息应尽量可重建

**来源：** 热力学、信息论、数据处理不等式。

解码、缩放、裁剪、颜色转换和日志脱敏都会丢失信息。不可逆步骤必须标记边界；可重建层与最终派生层不得混为一体。

Fovea 应用：

- OriginalEncoded、Decoded、Rendered 使用不同身份；
- Transform 失败保留已验证原编码；
- ContentID 描述完整 payload，不充当物理文件名；
- 日志只保留有限、脱敏信息；
- Derived 不能扩大 source 权限。

**证伪条件：** 不可逆转换后仍声称与原表示等价，或删除唯一可重建来源导致不必要重取网络。

**边界：** `no-store`、撤销和隐私要求可优先于可重建性，安全删除不是熵原则的例外，而是更高层约束。

### 3.8 FOVEA-LAW-008：阶段门是反应路径，不是文件目录

**来源：** 化学反应动力学、事务系统。

安全发布需要经过有顺序的资格门，类似反应路径中的中间态和活化条件。中间态可以存在，但不得被误认为最终产物；催化优化只能降低成本，不能绕过必要条件。

Fovea 应用：

```text
transport complete
→ metadata/content validation
→ probe/decode safety
→ generation check
→ blob/record transaction
→ transform validation
→ rendered publication
```

**证伪条件：** 半完成 body、未验证 metadata、撤销 generation 或 transform 半成品可进入 reusable state。

**边界：** 阶段门不要求每层一个类型；职责可合并，只要资格和回滚语义清晰。

### 3.9 FOVEA-LAW-009：演化通过变异与选择，而非版本堆积

**来源：** 进化生物学、Popper 式证伪。

测试套件的价值不在于保护现状，而在于淘汰错误变异。新抽象只有在竞争性实验中表现更好并保持不变量时才保留；失败原型应低成本删除。

Fovea 应用：

- 关键变异门要求所有有效 mutant 被杀死；
- cache 策略、decoder 后端和实验能力使用同 workload 比较；
- capability slot 不等于承诺；
- 无证据的抽象保持 Deferred 或被删除。

**证伪条件：** mutant 存活、测试只验证实现细节，或失败方案因沉没成本长期保留。

**边界：** 随机变异不是完整证明；mutant 集合必须持续随架构更新。

### 3.10 FOVEA-LAW-010：复杂性预算必须守恒并优先局部化

**来源：** 复杂性科学、网络科学、软件模块化。

复杂性不会因命名消失，只会在状态空间、依赖边、时间耦合和认知负担之间迁移。优化应减少跨边界传播，而不是把一个大文件机械拆成大量互相窥视的小文件。

Fovea 应用：

- 固定 stage，不引入通用 DAG；
- `package` 暴露内部共享而不泄漏公共 API；
- 结构门同时限制文件规模、函数复杂度、模块文件数和依赖环；
- HTTP、存储、像素和 UI 语义各有唯一所有者。

**证伪条件：** 拆分后依赖边、共享状态或调用顺序更多；局部修改需要理解更多模块。

**边界：** 指标只能发现热点，不能单独决定架构；穷举映射的高分支数与副作用状态机不可等同处理。

### 3.11 FOVEA-LAW-011：安全默认必须使外部性由产生者承担

**来源：** 经济学外部性、机制设计、安全工程。

产生风险、资源消耗或隐私成本的调用方必须显式承担配置与证据成本。安全路径应比危险路径更便宜，不能让全局系统为局部便利买单。

Fovea 应用：

- 默认 public-only ACL 与安全 URL policy；
- 凭证、Cookie、代理信任、后台联网和自动化公网实验必须显式配置；以真实图片体验为核心目的且明确告知联网行为的交互式 App 可以默认联网，但必须保留确定性离线模式、精确目的地策略和环境证据分级；
- custom transport/decoder 返回后由消费方复核 hard cap；
- `no-store`、namespace revoke 和敏感 Vary 失败关闭；
- 实验模块不进入默认依赖图。

**证伪条件：** 最简单 API 隐式扩大权限、共享身份或资源预算；插件可把成本转嫁给 Core。

**边界：** fail-closed 不能无差别牺牲可用性；应提供结构化失败和明确逃生口。网络是否默认启用取决于用户可见目的与副作用透明度：交互式图片浏览器的预期行为不同于 CI、后台任务或隐式遥测。

### 3.12 FOVEA-LAW-012：社会技术系统以可理解性维持一致

**来源：** 社会学、组织理论、文学与修辞学。

架构不仅由代码运行，也由维护者共同理解。名称、叙事顺序、术语和文档冲突会改变团队行为，最终改变系统。文档必须说明因果、边界和反例，而不是罗列功能。

Fovea 应用：

- Accepted ADR、活动规格和架构有明确优先级；
- 术语使用 FetchVariantKey、FetchExecutionKey、ContentID、RenderKey 等唯一语义名；
- 每项能力区分已实现、候选、实验和拒绝；
- 测试 ID 与追踪矩阵稳定；
- 注释解释“为什么”和失效条件，不逐句翻译代码。

**证伪条件：** 两份权威文档对同一行为给出不同答案，或维护者只能靠阅读实现猜测契约。

**边界：** 文档不能冻结错误设计；代码事实与文档冲突时必须显式修正文档和测试。

### 3.13 FOVEA-LAW-013：认识论状态必须显式

**来源：** 哲学、科学方法论、医学证据分级。

事实、推断、假设、类比和愿景必须分层。覆盖率、单元测试、Sanitizer、mutation、真机基准和生产观察提供不同强度的证据，不能相互冒充。

Fovea 应用：

- 文档使用 Proposed、Accepted、Experimental、Deferred 等状态；
- 性能结论绑定设备、workload、置信区间和原始 trace；
- 本地通过不能冒充远程 protected CI 或独立审计；
- “世界最好”必须被分解为可比较维度，而不是总体口号。

**证伪条件：** 结论强度高于证据强度，或未证明项被隐藏。

**边界：** 证据分级不应成为无限延期借口；高风险项必须提高证据，低风险项保持比例原则。

### 3.14 FOVEA-LAW-014：复杂问题必须寻找可复用金蛋

**来源：** 创新研究、设计科学、演化与文学隐喻。

复杂问题既是待解决故障，也是发现新模块、工具、测试方法和普遍不变量的实验场。每次重大修复都要询问：问题是否重复出现；是否存在更小、更稳定的抽象；是否应形成自动门禁；是否有反例证明不应抽象。

“金蛋”只有在以下条件满足时才成立：

- 至少解决一个真实问题，而非预想需求；
- 能描述复用边界和不适用范围；
- 有独立测试或工具证据；
- 减少未来重复劳动或错误面；
- 不扩大默认 API 或依赖成本；
- 可被删除、替换或降级。

**证伪条件：** 抽象只服务单一调用点、名字比行为更通用、隐藏关键差异，或维护成本大于重复成本。

**边界：** 发现“不要抽象”同样是金蛋；拒绝错误统一可保护领域边界。

| FOVEA-EGG-030 | Full jitter 与 Retry-After 下界共同治理重试同步 | 固定 full jitter、硬预算与碰撞工件 |
| FOVEA-EGG-031 | 数学理论必须登记采用、研究、候选或拒绝状态 | 15 项理论注册表、假设、反例和机器门禁 |
| FOVEA-EGG-032 | 预取任务身份必须同时版本化任务与完整目标几何 | 完整宽高/content-mode key 与 task UUID |
| FOVEA-EGG-033 | 可分享证据默认采用最小关联能力而非完整运行快照 | schema 3、短期 generation token、小时粒度与顺序号 |
| FOVEA-EGG-034 | 发布隐私边界必须同时覆盖源码声明、资源内容与最终二进制 | App PrivacyInfo、媒体元数据门与 Release 产物检查 |
| FOVEA-EGG-035 | 资源切换必须取消并汇合，跨进程锁必须可取消且有时限 | cancel-and-drain 与 staging lock timeout |
| FOVEA-EGG-036 | 比较实验必须在结果前锁定身份、数据集与统计计划 | comparator lock、commit/tree/dirty 身份、128 项选择清单与预注册计划 |

每项发现至少记录：

```text
触发问题
重复模式或异常
提炼出的资产
关联工程定律
代码/工具/文档落点
证明它有效的测试
复用边界
过度推广的失败方式
状态：promoted | deferred | rejected
```

发现流程：

1. **捕获异常**：记录失败测试、竞态、性能尖峰、文档冲突或重复人工步骤；
2. **寻找共同结构**：区分偶然相似与同一不变量；
3. **最小提炼**：优先提取值类型、协议、校验器、测试工具或门禁，不立即建立框架；
4. **竞争验证**：与保留重复实现、现有标准方案和删除方案比较；
5. **记录边界**：说明何时不应复用；
6. **持续淘汰**：失去复用价值、造成耦合或被语言/平台能力取代时降级或删除。

## 5. 反教条规则

以下做法默认拒绝：

- 用量子、熵、生态、涌现等词汇替代具体状态机；
- 因概念来自高深学科就降低证据要求；
- 为追求“统一理论”抹平 HTTP、存储、像素和 UI 的领域差异；
- 把覆盖率、复杂度分数或单一 benchmark 优化成目标函数；
- 为未来可能复用而提前建立通用框架；
- 用更多文档掩盖无法运行的实现；
- 把 AI 的广泛知识当作无误权威；
- 把一次成功类比写成永久架构定律。

## 6. 变更审查问题

每次 R2/R3 变更至少回答：

1. 它保护或改变了哪些不变量？
2. 哪些资源被创建、持有、转移和释放？
3. 副作用的最早合法发生点是什么？
4. 在取消、撤销、崩溃和极值输入下，系统会收敛到什么状态？
5. 哪个观测能够区分正确因果与巧合？
6. 是否把局部成本转嫁给其他 namespace、模块、调用方或未来维护者？
7. 是否产生值得登记的金蛋；若没有，为什么不应抽象？
8. 哪个反例会推翻当前设计？
9. 文档、测试、变异目录和证据门是否同步？

## 7. 治理

`engineering-knowledge.json` 由 `scripts/check-engineering-knowledge.py` 验证，并进入统一 `scripts/verify.sh`。原则或金蛋不能只改 JSON：活动元规格必须出现对应 ID；所有引用的源码路径和测试 ID 必须存在；promoted 金蛋必须有真实资产和测试证据。

新增工程定律需要说明它不能被现有定律表达的原因。删除或合并定律必须保留迁移说明。金蛋可以被标记为 deferred 或 rejected，项目不以条目数量评价创新。
